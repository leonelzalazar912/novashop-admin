### Acción `remove`

Se implementó la acción:

`remove`

Quitar un usuario significa eliminar su membresía de una tienda, no eliminar automáticamente su cuenta global.

Comportamiento:

- elimina el registro correspondiente de `store_members`;
- no elimina la cuenta de Supabase Auth;
- no elimina el registro de `profiles`;
- no permite que un Administrador quite a un Propietario;
- protege al último Propietario activo;
- protege al último Administrador activo;
- impide que el usuario autenticado se quite a sí mismo;
- devuelve `removedUserId` para que el frontend pueda retirar el usuario de la tabla.

### Situación inicial

### Diagnóstico del esquema real sin Docker

No hay Docker Desktop instalado en el entorno de desarrollo, por lo que `supabase db pull` y `supabase db dump` (que dependen de un contenedor para el shadow database / `pg_dump`) no funcionan. Tampoco hay `psql` ni un cliente Postgres local. Se probó traer el esquema vía el endpoint OpenAPI de PostgREST con la anon key, pero el gateway nuevo de Supabase lo bloquea explícitamente para claves no-secretas.

Se resolvió consultando `information_schema.columns`, `pg_policies` y `pg_class` directamente desde el SQL Editor del dashboard (el usuario corrió las queries, se pegó el resultado en el chat). De ahí se confirmó:

- Esquema real de `products`, `product_images`, `product_suppliers`, `stores` (columnas exactas, no las que se suponían).
- Las políticas RLS de lectura pública para `products`, `product_images`, `brands`, `categories`, `stores`, `store_settings` **ya existían** (`active = true AND published = true` para productos, patrón similar para el resto) — no hubo que crearlas.
- Tablas que no se sabía que existían: `stores`, `store_settings`, `order_addresses`, `order_status_history`, `payments`, `shipments`, `audit_logs` — la base está más avanzada de lo que documentaba `NovaShop_Contexto.txt`.
- Para lecturas puntuales sin necesidad de pedirle al usuario que corra SQL, se usó la anon/publishable key directo contra PostgREST vía `curl` (funciona porque las tablas relevantes tienen lectura pública activada) — por ejemplo para confirmar el `slug`/`id` real de la tienda (`novashop-demo`, `81f5b4cb-1954-41de-8954-51ec1b922dea`) y para diagnosticar problemas de datos sin intervención del usuario.

### Decisiones tomadas con el usuario antes de tocar código

1. Catálogo genérico, no específico de gaming: los atributos propios de cada rubro (developer/género/año, talles/colores, etc.) van en una columna `metadata jsonb`, no como columnas fijas de `products`.
2. La lectura pública anónima del catálogo se resuelve por `store_id`, con `store_slug` fijo en `storeConfig.ts` (no un UUID hardcodeado) — preparado para resolver por dominio en un futuro multi-tienda.
3. Los campos "de marketing" que no existen en el schema real (`originalPrice`, `discount`, `rating`, `reviews`, `badge`) quedan **fuera de alcance** de esta migración, no se agregan columnas nuevas para ellos.
4. Storage de imágenes: bucket público `product-images`, con borrado del archivo viejo del bucket cuando se reemplaza la imagen de un producto (`storage.remove()`), desde el arranque (no como mejora futura).

### Bug encontrado y corregido: `published` no editable

`useProducts.ts` tenía `published: false` hardcodeado al crear un producto, nunca se seleccionaba al leer ni se enviaba al editar — todo producto nuevo nacía invisible en la tienda pública sin manera de cambiarlo desde la UI. Se agregó `published` al modelo, al `select`, al `insert` y al `update`, y un toggle "Publicado/Borrador" en `ProductForm.tsx` (default **Borrador**, decisión explícita del usuario: publicar tiene que ser un acto consciente).

### Migración de imágenes: base64 → Supabase Storage

`ProductForm.tsx` convertía el archivo subido a base64 con `FileReader` y lo guardaba tal cual en `product_images.image_url` — se detectó al ver que una sola consulta con imagen pesaba 6.4 MB. Se migró a Supabase Storage:

- `ProductForm.tsx`: ya no convierte a base64; guarda el `File` en estado y previsualiza con `URL.createObjectURL` (se libera con `revokeObjectURL` al desmontar).
- `useProducts.ts`: nuevos helpers `uploadProductImage`/`removeProductImage`. `handleAddProduct`/`handleUpdateProduct` suben el archivo a Storage antes de escribir `product_images`; `handleUpdateProduct` borra la imagen anterior del bucket si cambió.

### Bug encontrado y corregido: borrado de productos no hacía nada

El usuario reportó que borrar un producto de prueba ("play5") no hacía nada visible. Diagnóstico confirmado por consola del navegador: error 409, Postgres `23503` (foreign key violation) porque `stock_movements` todavía referenciaba al producto. Causas combinadas:

- `handleDeleteProduct` borraba la fila de `products` directo, sin borrar antes `product_images`/`product_suppliers`/`inventory_levels`.
- `ProductsPage.tsx` nunca leía el `error` que devuelve `useProducts()` — cualquier fallo se perdía en silencio.

Se implementó un patrón híbrido, acordado con el usuario antes de tocar código:

- Cascada real (borrado automático) para `product_images`, `product_suppliers`, `inventory_levels` — son "estado actual" sin valor propio sin el producto. También se borra el archivo de Storage si corresponde.
- Bloqueo + mensaje claro (mismo patrón que ya existía para `order_items` vía `hasOrdersByProduct`) para `stock_movements` y `purchase_items` — son historial/auditoría, no deben desaparecer. Se agregaron `hasStockMovementsByProduct`/`hasPurchaseItemsByProduct` a `useDataIntegrity.ts` y se llaman desde `ProductsTable.tsx` antes de confirmar el borrado.
- Se agregó un toggle "Activar"/"Desactivar" (`toggleProductActive`, mismo patrón que ya existía en Clientes) como alternativa al borrado físico cuando está bloqueado por integridad referencial.
- `ProductsPage.tsx` ahora renderiza el `error` del hook con el componente `Message` — cualquier fallo futuro se va a ver en pantalla, no a perderse en la consola.
- De paso se sacó un `window.confirm` duplicado que tenía `handleDeleteProduct` (ya confirmaba `ProductsTable.tsx` antes de llamarlo).

"play5" se borró manualmente por SQL (tenía movimientos de stock de pruebas anteriores) antes de que el fix estuviera listo.

### Bugs preexistentes corregidos (sin relación con esta migración)

Al instalar `typescript` como devDependency (el proyecto no lo tenía, tampoco tenía `tsconfig.json` — `npm run build` nunca chequeó tipos, solo transpila con esbuild) y correr un chequeo de tipos real por primera vez en el historial del proyecto, aparecieron 12 errores preexistentes, confirmados por `git log` como anteriores a esta sesión:

- 7 imports rotos a `../data/productsData` en `modules/admin/components/{CategoryChart,DashboardCharts,DashboardWidgets,InventoryPieChart,LowStockProducts,RecentOrders}.tsx` y `modules/admin/hooks/useDashboard.ts` — asumían un `modules/admin/data/productsData.ts` central que nunca existió; el archivo real está en `modules/admin/products/data/productsData.ts`. Corregido: solo la línea del import en cada archivo.
- Mezcla `id: number` / `id: string` en `BrandsPage.tsx`, `CategoriesPage.tsx`, `CategoryForm.tsx`, `SuppliersPage.tsx` — resabio de cuando esos módulos usaban `localStorage` con ids `Date.now()`; el resto de cada módulo (tipos, hooks, tablas) ya estaba migrado a `string`, solo las funciones-wrapper de la `*Page.tsx` (y la prop `onUpdateCategory` de `CategoryForm.tsx`) quedaron con la firma vieja. Corregido: solo las anotaciones de tipo, cero cambio de lógica.
- `handleAddBrand`/`handleAddSupplier` en `BrandsPage.tsx`/`SuppliersPage.tsx` sin `await`: comparaban una `Promise<boolean>` (siempre truthy) en vez de esperar el resultado real, así que el mensaje "Ya existe una marca/proveedor con ese nombre" nunca se mostraba aunque la creación fallara por duplicado. Corregido agregando `async`/`await`.

Ninguno de estos tres grupos tiene relación con la migración de `Product`: sobrevivieron porque nunca hubo un chequeador de tipos corriendo sobre el proyecto, y tanto un `import type` roto como una anotación de tipo incorrecta se borran por completo al transpilar (no rompen el bundle de Vite/esbuild, solo son visibles para `tsc`).

## Sesión 31/07/2026 (continuación) — Auditoría de schema_dump.sql vs. base real

Se retomó el pendiente dejado al cierre de la sesión anterior (Architecture.md § Deuda, punto 1): confirmar si el constraint `payments_provider_reference_unique` (documentado como aplicado desde el 29/07 pero encontrado ausente en la validación de Mercado Pago) era un caso aislado o síntoma de un desfase más amplio entre `schema_dump.sql` y la base real de `novashop-development`.

Sin Docker disponible (confirmado de nuevo intentando `npx supabase db dump --linked`, mismo error de siempre), se auditó a mano: se extrajeron de `schema_dump.sql` los 120 constraints (25 PK + 14 UNIQUE + 27 CHECK + 54 FK), 61 índices (39 auto-creados por PK/UNIQUE + 22 explícitos), 6 funciones y 19 triggers declarados, y se compararon uno por uno contra el resultado de correr `pg_constraint`/`pg_indexes`/`pg_proc`/`pg_trigger` directamente en el SQL Editor de `novashop-development`.

**Resultado: coincidencia total.** Las cuatro categorías cerraron con el mismo conteo y los mismos nombres/definiciones en ambos lados — ningún constraint, índice, función o trigger documentado faltaba en la base real, y no apareció ningún elemento extra sin documentar. Se confirmó puntualmente que `payments_provider_reference_unique` sigue presente (fix de la sesión anterior firme).

**Conclusión**: el gap encontrado con esa constraint fue un incidente aislado (probablemente se corrió/validó solo contra el proyecto Supabase vacío usado para probar el dump, y nunca se replicó a mano contra la base real), no la punta de un problema sistemático de sincronización. No hace falta seguir auditando el resto del schema por esta preocupación puntual.
