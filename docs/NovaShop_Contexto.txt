Resumen de lo que cambió desde el 14/07:

- **Usuarios**: migrado por completo a Supabase (Edge Function `manage-users`, permisos por rol, invitaciones). Sesiones del 21/07 y 23/07.
- **Clientes, Pedidos, Marcas, Categorías, Proveedores, Compras**: ya estaban migrados a Supabase antes incluso de esta sesión (confirmado revisando el código, no quedaba nada de `localStorage` en esos módulos).
- **Productos**: además de estar en Supabase, ahora tiene `published`/`active` editables desde la UI, borrado con integridad de datos (cascada + bloqueo según corresponda), e imágenes reales en Supabase Storage (ya no base64). Sesión del 28-29/07. Y desde la continuación del 29/07, `modules/admin/products` usa el tipo `AdminProduct` unificado (antes tenía su propio tipo local con relaciones como texto plano).
- **Catálogo público (storefront)**: dejó de ser mock. Se conectó a las tablas reales de Supabase, resolviendo la tienda por `slug` en vez de un ID fijo. Sesión del 28-29/07.
- **Checkout público**: conectado de punta a punta (sesión del 29/07, continuación). Confirmar en `PaymentScreen` dispara la función de Postgres `checkout_create_order` — crea la orden, descuenta stock atómicamente, todo o nada. `CompletedScreen` ya muestra datos reales del pedido, no hardcodeados.
- **`tsconfig.json` real**: creado (no existía ninguno). `npm run build` ahora tipa en `strict` antes de bundlear.
- **Schema versionado**: el schema completo de Supabase (tablas, RLS, funciones, políticas, Storage) está en `supabase/schema_dump.sql`, generado a mano (no hay Docker para `supabase db dump`) y validado corriéndolo en un proyecto vacío.
- **Mercado Pago — en progreso, NO terminado**: se crearon y desplegaron dos Edge Functions (`mercadopago-create-payment`, `mercadopago-webhook`), la conexión con la API de MP funciona, pero **el pago con tarjeta todavía no se validó de punta a punta** (error `Invalid payment_method_id` sin resolver del todo al cierre de esta sesión). Próximo paso: construir el Payment Brick en el frontend. Ver Architecture.md § Estado de la migración para el detalle completo — no dar esto por terminado.
- **Modelo `Product`**: unificado entre storefront y admin, incluyendo ya `modules/admin/products` (ver arriba).
- **Ya existen decenas de tablas en Supabase con RLS activado**, incluyendo varias que ni se sabía que existían (`stores`, `store_settings`, `payments`, `shipments`, `audit_logs`, etc. — ver Architecture.md § Modelo de datos). La sección 7 de este archivo ("no se creó ninguna tabla todavía") quedó obsoleta.
- Se instaló `typescript` como devDependency (no estaba) y se corrió un chequeo de tipos real por primera vez en el proyecto, lo que sacó a la luz 12 bugs preexistentes (imports rotos, mezcla de tipos de `id`, un `await` faltante) — todos corregidos.

## 1. Visión del producto

NovaShop será una plataforma comercial adaptable a pequeños y medianos negocios de cualquier rubro.

No es solamente una tienda online. El producto final combina:

- Ecommerce público.
- Panel administrativo.
- Gestión de productos e inventario.
- Compras y proveedores.
- Pedidos, ventas, clientes y caja.
- Reportes.
- Usuarios, roles y permisos.
- Configuración personalizada para cada comercio.

Debe poder utilizarse para videojuegos, ropa, celulares, perfumería, librería, repuestos, electrónica, hogar y otros rubros sin modificar el código fuente.

El objetivo final es comercializar NovaShop como una base reutilizable y configurable para diferentes negocios.

8. Decisiones tomadas
Decisión 1 — Supabase será la infraestructura definitiva
La aplicación dejará de usar localStorage como persistencia principal.

localStorage podrá utilizarse únicamente para:

Preferencias no sensibles.

Caché.

Estado temporal del carrito, cuando corresponda.

Configuración visual local no crítica.

Decisión 2 — No crear más módulos antes de la infraestructura
Se detuvo el inicio de Ventas y de otros módulos.

Antes de continuar se debe:

Auditar los modelos actuales.

Diseñar la base completa.

Crear autenticación y seguridad.

Crear una capa de servicios.

Migrar los módulos existentes.

Decisión 3 — NovaShop será multiempresa
Los datos comerciales deberán pertenecer a un comercio.

Las tablas relevantes deberán incluir una relación equivalente a:

store_id
Los usuarios solo podrán acceder a comercios donde tengan autorización.

Decisión 4 — Usar UUID
Los IDs definitivos no deben generarse con:

Date.now()
Supabase/PostgreSQL generará UUID.

Decisión 5 — No guardar relaciones como texto
No usar como relación definitiva:

category: string
brand: string
supplier: string
Usar identificadores:

category_id
brand_id
supplier_id
Decisión 6 — Separar interfaz y persistencia
Los componentes React no deben acceder directamente a Supabase.

Flujo recomendado:

Componente
→ hook
→ servicio o repositorio
→ Supabase
Decisión 7 — Diseñar antes de ejecutar SQL
No crear tablas manualmente una por una.

Primero revisar todos los modelos necesarios.

Después preparar y revisar un diseño consolidado.

Finalmente ejecutar una migración SQL inicial.

17. Resumen rápido para retomar

[REESCRITO el 31/07/2026, tercera vez — ver nota de actualización al inicio del archivo para el detalle completo.]

NovaShop es un Ecommerce + ERP genérico y multiempresa que se pretende comercializar.

La migración de `localStorage` a Supabase que preveía este documento **ya se hizo por completo**: todos los módulos del admin (productos, categorías, marcas, proveedores, compras, clientes, pedidos, usuarios) leen y escriben en Postgres real, con RLS activado en cada tabla y modelo multiempresa por `store_id`, y `modules/admin/products` ya usa el tipo `AdminProduct` unificado. Usuarios tiene además una Edge Function (`manage-users`) con permisos por rol. El catálogo público de la tienda se conectó a Supabase (sesión 28-29/07) y **el checkout también** — confirmar la compra crea una orden real vía la función de Postgres `checkout_create_order` (atómica: valida y descuenta stock, crea la orden, todo o nada).

Supabase tiene hoy más de 20 tablas reales (multiempresa, catálogo, inventario, compras, clientes/pedidos, auditoría), un bucket de Storage (`product-images`), la Edge Function `manage-users`, y dos Edge Functions más para Mercado Pago (`mercadopago-create-payment`, `mercadopago-webhook`). El schema completo está versionado en `supabase/schema_dump.sql` (validado corriéndolo en un proyecto vacío), y el proyecto ya tiene `tsconfig.json` real con `strict: true`.

El desarrollo de módulos nuevos (Ventas, Caja, Reportes) sigue congelado hasta que se decida explícitamente retomarlo — eso no cambió.

**Mercado Pago ya se terminó y se validó de punta a punta (sesión del 31/07/2026).** Se construyó el Payment Brick (`CardPayment` de `@mercadopago/sdk-react`) en `PaymentScreen.tsx` — resuelve automáticamente `payment_method_id`/`issuer_id` a partir del BIN de la tarjeta, eliminando el problema que se venía debuggeando por curl. Se confirmó con pagos de test reales (uno aprobado, uno rechazado con reintento sobre la misma orden) que `orders.payment_status` y `payments` quedan consistentes. Ver `docs/Architecture.md` § Estado de la migración → Mercado Pago para el detalle completo.

**El próximo trabajo grande ahora**: auditar `schema_dump.sql` contra el estado real de `novashop-development`. En la validación de Mercado Pago se descubrió que un constraint documentado como ya aplicado nunca se había ejecutado contra la base real — no hay garantía de que sea el único caso. Ver `docs/Architecture.md` § Deuda, punto 1.
