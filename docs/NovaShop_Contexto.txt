Este archivo se escribió originalmente el 14/07/2026 y varias secciones de abajo (especialmente la 5, la 7, la 11 y la 12) describen un estado **anterior** a varias sesiones de migración importantes que ya pasaron. La fuente de verdad técnica actualizada es **`docs/Architecture.md`** (estructura, modelo de datos real, decisiones vigentes) — este archivo sigue siendo útil para la visión de producto y las reglas de trabajo, pero para el estado técnico exacto, confiar en `Architecture.md` y en `docs/bitacora-desarrollo.txt` (log sesión por sesión) por encima de lo que diga la sección 5 de acá abajo.

Resumen de lo que cambió desde el 14/07:

- **Usuarios**: migrado por completo a Supabase (Edge Function `manage-users`, permisos por rol, invitaciones). Sesiones del 21/07 y 23/07.
- **Clientes, Pedidos, Marcas, Categorías, Proveedores, Compras**: ya estaban migrados a Supabase antes incluso de esta sesión (confirmado revisando el código, no quedaba nada de `localStorage` en esos módulos).
- **Productos**: además de estar en Supabase, ahora tiene `published`/`active` editables desde la UI, borrado con integridad de datos (cascada + bloqueo según corresponda), e imágenes reales en Supabase Storage (ya no base64). Sesión del 28-29/07.
- **Catálogo público (storefront)**: dejó de ser mock. Se conectó a las tablas reales de Supabase, resolviendo la tienda por `slug` en vez de un ID fijo. Sesión del 28-29/07.
- **Modelo `Product`**: unificado entre storefront y admin del lado del tipo público (`src/types/product.ts`), con `AdminProduct` para los campos internos. El módulo `modules/admin/products` en sí todavía no usa `AdminProduct` (sigue con su tipo local), queda pendiente.
- **Ya existen decenas de tablas en Supabase con RLS activado**, incluyendo varias que ni se sabía que existían (`stores`, `store_settings`, `payments`, `shipments`, `audit_logs`, etc. — ver Architecture.md § Modelo de datos). La sección 7 de este archivo ("no se creó ninguna tabla todavía") quedó obsoleta.
- Se instaló `typescript` como devDependency (no estaba) y se corrió un chequeo de tipos real por primera vez en el proyecto, lo que sacó a la luz 12 bugs preexistentes (imports rotos, mezcla de tipos de `id`, un `await` faltante) — todos corregidos. Sigue faltando un `tsconfig.json` real.

Las secciones 11 y 12 (modelos por revisar / próximo paso exacto) están reescritas más abajo para reflejar esto. No siguas el "próximo paso" viejo que decía auditar `brandsData`/`clientsData`/`ordersData`/`usersData`/`cartTypes` — los cinco ya están resueltos.

**Este archivo es ahora el único "documento maestro" del proyecto.** Existía un segundo documento con el mismo propósito, `estructura-proyecto.txt` (en la raíz del repo), que se usó como referencia en la sesión del 21/07/2026 — quedó deprecado el 29/07/2026 para no tener dos fuentes de contexto que puedan decir cosas distintas. ## 1. Visión del producto

NovaShop será una plataforma comercial adaptable a pequeños y medianos negocios de cualquier rubro.

No es solamente una tienda online. El producto final combina:

- Ecommerce público.
- Panel administrativo.
- Gestión de productos e inventario.
- Compras y proveedores.
- Pedidos, ventas, clientes y caja.
- Reportes.
- Usuarios, roles y permisos.
- Configuración personalizada para cada comercio.

Debe poder utilizarse para videojuegos, ropa, celulares, perfumería, librería, repuestos, electrónica, hogar y otros rubros sin modificar el código fuente.

El objetivo final es comercializar NovaShop como una base reutilizable y configurable para diferentes negocios.

8. Decisiones tomadas
Decisión 1 — Supabase será la infraestructura definitiva
La aplicación dejará de usar localStorage como persistencia principal.

localStorage podrá utilizarse únicamente para:

Preferencias no sensibles.

Caché.

Estado temporal del carrito, cuando corresponda.

Configuración visual local no crítica.

Decisión 2 — No crear más módulos antes de la infraestructura
Se detuvo el inicio de Ventas y de otros módulos.

Antes de continuar se debe:

Auditar los modelos actuales.

Diseñar la base completa.

Crear autenticación y seguridad.

Crear una capa de servicios.

Migrar los módulos existentes.

Decisión 3 — NovaShop será multiempresa
Los datos comerciales deberán pertenecer a un comercio.

Las tablas relevantes deberán incluir una relación equivalente a:

store_id
Los usuarios solo podrán acceder a comercios donde tengan autorización.

Decisión 4 — Usar UUID
Los IDs definitivos no deben generarse con:

Date.now()
Supabase/PostgreSQL generará UUID.

Decisión 5 — No guardar relaciones como texto
No usar como relación definitiva:

category: string
brand: string
supplier: string
Usar identificadores:

category_id
brand_id
supplier_id
Decisión 6 — Separar interfaz y persistencia
Los componentes React no deben acceder directamente a Supabase.

Flujo recomendado:

Componente
→ hook
→ servicio o repositorio
→ Supabase
Decisión 7 — Diseñar antes de ejecutar SQL
No crear tablas manualmente una por una.

Primero revisar todos los modelos necesarios.

Después preparar y revisar un diseño consolidado.

Finalmente ejecutar una migración SQL inicial.

11. Modelos que faltan revisar

[SECCIÓN OBSOLETA — reescrita el 29/07/2026, ver nota de actualización al inicio del archivo]

La lista original (`brandsData.ts`, `clientsData.ts`, `ordersData.ts`, `usersData.ts`, `cartTypes.ts`) ya está resuelta por completo:

- `brandsData.ts`, `clientsData.ts`, `ordersData.ts`, `usersData.ts`: los cuatro módulos ya están migrados a Supabase (tablas reales, relaciones por ID, UUID). Usuarios además tiene Edge Function con permisos por rol.

- `src/app/components/data.ts`: ya no se usa en ningún lado (el catálogo público se conectó a Supabase) — candidato a borrar, no a revisar.
- `src/config/categories.ts`: revisado — su export `categories` (Electrónica/Ropa/Perfumería/Juguetes) confirmado sin ningún uso en el código. Candidato a limpiar.
- `src/config/business.ts`: todavía no revisado a fondo, pero es config estática de la tienda (contacto, dirección, moneda) sin relación con ninguna tabla — bajo riesgo.

El modelo de datos real (columnas, relaciones, RLS) ya no es un diseño preliminar: existe y está documentado en `docs/Architecture.md` § Modelo de datos en Supabase, extraído directamente de `information_schema` el 28/07/2026.

Lo que sigue sin resolver, y si vale la pena, es otra cosa: `modules/admin/products` no usa todavía el `AdminProduct` unificado (ver Architecture.md § Deuda, punto 1) — es una refactorización de un módulo ya probado, no un modelo por diseñar.

17. Resumen rápido para retomar

[REESCRITO el 29/07/2026 — la versión anterior de esta sección decía "todavía no existen tablas ni se ejecutó SQL", que ya no es cierto. Ver nota de actualización al inicio del archivo para el detalle completo.]

NovaShop es un Ecommerce + ERP genérico y multiempresa que se pretende comercializar.

La migración de `localStorage` a Supabase que preveía este documento **ya se hizo**: todos los módulos del admin (productos, categorías, marcas, proveedores, compras, clientes, pedidos, usuarios) leen y escriben en Postgres real, con RLS activado en cada tabla y modelo multiempresa por `store_id`. Usuarios tiene además una Edge Function (`manage-users`) con permisos por rol. El catálogo público de la tienda (que hasta el 27/07 seguía siendo mock) también se conectó a Supabase en la sesión del 28-29/07/2026.

Supabase tiene hoy más de 20 tablas reales (multiempresa, catálogo, inventario, compras, clientes/pedidos, auditoría), un bucket de Storage (`product-images`) y la Edge Function `manage-users` desplegada. El modelo de datos completo, con columnas reales, está en `docs/Architecture.md` § Modelo de datos en Supabase — no hace falta re-derivarlo desde los archivos `data/*.ts` del frontend como planteaba este documento originalmente.

El desarrollo de módulos nuevos (Ventas, Caja, Reportes) sigue congelado hasta que se decida explícitamente retomarlo — eso no cambió.

El siguiente paso real (ver sección 12 y `docs/bitacora-desarrollo.txt`, sesión 28-29/07/2026) es cargar productos reales desde el admin y validar el catálogo público en el navegador, y después decidir entre unificar `modules/admin/products` al tipo `AdminProduct` común o crear un `tsconfig.json` real para el proyecto (no existe ninguno todavía).
